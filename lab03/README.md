# Лабораторная работа 3

Вариант 7. Управление потоками и экспериментальная оценка вероятностей в игре в кости.
Linux / Ubuntu в WSL 2; программа на C17, нативные потоки POSIX pthread.

## Правила и входные данные

Каждый игрок бросает две честные шестигранные кости K раз.
Побеждает игрок с большей итоговой суммой. Равные суммы считаются ничьей.
Программа моделирует только оставшиеся туры и выводит частоты трёх исходов:
победы первого, победы второго и ничьей. Каждая частота — число исходов / число опытов.
Вероятности выводятся в диапазоне 0..1, например 0.607070 означает 60.707%.

`ТУР` означает число полностью завершённых туров, от 0 до K включительно.
Если начался третий тур, но бросков в нём ещё не было, надо передать 2.
Оба игрока должны завершить одинаковое число туров. Частично сыгранный тур не поддерживается.
При ТУР=K результат уже определён текущими очками.

```sh
make
./build/dice --threads 4 --seed 42 10 3 21 18 100000
./build/dice --help
```

Позиционные аргументы: `K ТУР ОЧКИ1 ОЧКИ2 ОПЫТЫ`.
Флаги можно указывать до или после них.

- `--threads N` обязателен: максимум одновременно существующих потоков, включая основной.
- `--seed S` — начальное состояние генератора, по умолчанию 1. Повторный запуск воспроизводим.
- `--quiet` — убрать сообщения с PID/TID из stderr для замеров времени.
- K: 1..1 000 000 000; ТУР: 0..K; ОПЫТЫ: 1..1 000 000 000 000.
- Очки каждого игрока: от 2*ТУР до 12*ТУР, при ТУР=0 оба счёта равны нулю.
- N: 1..1024; S: 0..18446744073709551615.

Это проверки диапазона, а не обещание быстрого расчёта для максимальных значений.
Сложность: O(ОПЫТЫ * (K - ТУР)); память: O(N). Счётчики и очки — uint64_t.

Пример с seed=42: побед первого 60598, второго 35264, ничьих 4138.
Точные актуальные значения приведены в сохранённом журнале запуска и отчёте.
Сумма трёх счётчиков всегда равна числу опытов. Сумма округлённых частот может отличаться от 1 на последнем разряде.

## Структура и синхронизация

```text
lab03/
  Makefile, README.md, BENCHMARK.md
  include/game.h
  src/main.c, options.c, game.c
  scripts/benchmark.py
  report/ОСИ_Отчет_ЛР3_Жензиров_Илья.docx
  build/       сгенерированные программы и объектные файлы
  artifacts/   сгенерированные журналы и исходные замеры
```

`options.c` разбирает и проверяет аргументы. `main.c` измеряет время и выводит результаты.
`game.c` делит опыты на почти равные непрерывные диапазоны (разница не больше одного опыта).
Создаются p-1 дополнительных потоков, основной обрабатывает последний диапазон.
p=min(N,ОПЫТЫ), поэтому лимит учитывает основной поток и пустых работников нет.

Каждый работник читает общие неизменяемые параметры и изменяет только свои счётчики.
Основной поток суммирует их строго после pthread_join: join обеспечивает завершение и видимость записей.
Общий счётчик на каждом броске не нужен, поэтому мьютекса в вычислительном цикле нет.
Потоки не используют общий rand() и не обращаются к общему изменяемому состоянию генератора.
Одна строка диагностики выводится одним fprintf; стандартная библиотека защищает FILE при работе потоков.
При ошибке pthread_create основной поток дожидается всех уже созданных работников, освобождает память
и возвращает ошибку без частичного результата. Ошибки pthread возвращаются непосредственно, а не через errno.
Неожиданный отказ join завершает весь процесс: освобождать память потенциально живого потока небезопасно.

## Случайные числа и точность

Для каждого опыта вычисляется собственное состояние из seed и глобального номера опыта.
Поэтому при том же seed изменение N и порядка планирования не меняет счётчики.
Использован генератор SplitMix64: сложение, сдвиги, XOR и умножение uint64_t.
Переполнение беззнакового числа здесь намеренное, по модулю 2^64.
Первые четыре значения 0..3 отвергаются перед `% 6`: количество остальных значений кратно 6,
что устраняет смещение простого остатка. Затем результат 0..5 сдвигается в 1..6.
Генератор предназначен для моделирования, не для криптографии.

Монте-Карло даёт приближённые вероятности. Для N опытов стандартная ошибка частоты p
оценивается как sqrt(p*(1-p)/N). При N=100000 её максимум около 0.00158 (0.158 процентного пункта).
Изменение seed даёт другую реализацию выборки; увеличение числа потоков при фиксированном N точность не повышает.
Для одного оставшегося тура при равных очках точные вероятности: 575/1296 у каждого игрока и 146/1296 для ничьей.
Эти значения получаются полным перебором четырёх костей.

## Сборка и демонстрация

```sh
sudo apt install build-essential strace python3
make
make run
make trace
make benchmark
```

Для сборки программы нужны GCC, Make и pthread.
Python 3 используется только для автоматизации замеров, не в программе.
`make trace` сохраняет clone/clone3, futex, gettid и завершение потоков в `artifacts/trace.log`;
численные результаты находятся в `results.txt`, сообщения PID/TID — в `threads.log`.
В Linux pthread_create обычно виден как clone3/clone, а pthread_join может ожидать через futex.
Вызов futex при ожидании уже завершённого потока может отсутствовать.

Показать потоки средствами ОС (запускать из lab03):

```sh
mkdir -p artifacts
./build/dice --threads 4 100 0 0 0 20000000 > artifacts/observed-results.txt 2> artifacts/observed-threads.log &
pid=$!
ps -L -p "$pid" -o pid,tid,nlwp,stat,comm
wait "$pid"
```

Если программа успела завершиться, увеличьте число опытов. NLWP — число потоков процесса;
PID общий, TID у каждого свой. Для основного потока PID=TID.
Для записи в artifacts предварительно выполните `mkdir -p artifacts` (make trace тоже создаёт каталог).
В реально проведённой проверке ps показал NLWP=4 и четыре TID.

Исследование производительности: [BENCHMARK.md](BENCHMARK.md).
`make benchmark` выполняет 75 замеров: 3 набора данных × 5 лимитов потоков × 5 повторов.
Медианы, ускорение и эффективность сохраняются в BENCHMARK.md, сырые данные — в artifacts/benchmark_raw.csv.
Описание машины — artifacts/environment.txt. Копии CSV и описания среды для сохранения в Git находятся в report/measurements. Повторный запуск перезаписывает результаты исследования.
`build/` и `artifacts/` исключены из Git. `make clean` удаляет только build.
